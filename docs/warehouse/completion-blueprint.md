## 1. Решения владельца и архитектуры

**Владелец (2026-11-11):**
- Бэкапы, учения DR и симуляция алертов ёмкости: скрыть из меню, код не удалять.
- Экраны с данными только в памяти остаются в меню. До перевода на базу на каждом ярко-красная плашка
  (EN и LT): «Данные на этом экране не сохраняются и пропадут при перезапуске». Плашку убрать, когда экран переведён.
- Отгрузка: перевозчик и номер отслеживания вводятся вручную для любого перевозчика, выдуманных номеров нет.
- Товар уходит из остатков при dispatch.
- Allocate резервирует товар. Автоматического истечения резерва нет.
- Карантин: «вернуть на склад», «вернуть поставщику», «списать». Права у QC и менеджера.
- Партии: ничего не менять. Партия остаётся атрибутом, ключ остатка прежний, FEFO нет.
- Перемещение между складами остаётся одним шагом, но запись должна стать атомарной.
- Agnum остаётся снимком. Документов в Agnum по операциям нет, запись в Agnum выключена.
- Приход: кнопка «закрыть с недостачей». Частичный отбор оставляет задание на остаток.

**Владелец (2026-11-11, после C7):**
- Склад один. Перемещение — между ячейками этого склада (заменяет решение «между складами» выше).
- Регистр стоимости: админ может применить перестройку при расхождении — после просмотра изменений, с причиной, с записью в журнал.
- QA-данные на test остаются, ничего не чистить.

**Архитектура (Claude):**
- Переход всех операций на `StockLedger.RecordMovement` не делаем. Каждое исправление меняет остатки тем же путём,
  каким уже работает соседняя операция:
  - событие корректировки как в `AdjustmentsController.cs:125-152` (`stock-adjustment:{id}`);
  - перемещение через `TransferServices.AppendStockMovementAsync` или так же, как `PutawayController`;
  - операционные события (`GoodsReceivedEvent`, `QCPassedEvent`, `QCFailedEvent`, `PickCompletedEvent`), если поток уже на них.
- Событие, которое должно менять остаток, обязано попасть в Marten. Только шина (`IEventBus.PublishAsync`) остаток
  не меняет. Шину оставить там, где на неё уже подписаны.
- EF и Marten в одной операции: одна транзакция Postgres (общее соединение, `SessionOptions.ForTransaction`), если обе
  базы — одна база. Если нет, сначала Marten, потом EF, повтор идемпотентный. Ошибки не глотать.
- Правило виртуальных ячеек: физическими считаются ячейки с `IsVirtual = false`, кроме `AGNUM` и `IN_TRANSIT_*`.
  Одна общая функция на все экраны: Available Stock, Stock Level, Location balance, Stock dashboard, Dashboard
  (overview, category, warehouse), 2D/3D. Только физические ячейки доступны для резерва и продажи.
- Новая виртуальная ячейка `CUSTOMER` (сид миграцией, `IsVirtual = true`) — назначение отгрузки.
- Миграции EF разрешены только для таблиц и сида из этого файла. Каждая миграция обратима.

## 2. Целевые потоки (контракт с дизайнером)

Именно так должен работать код после всех этапов.

1. **Приход.** siunta → Priimti → `QC_HOLD` (QC у товара) или `RECEIVING` → QC pass → `RECEIVING` → Putaway в ячейку.
   Частичный приход, «закрыть с недостачей». Сверх ожидаемого нельзя. Закупочная цена обязательна → WAC.
2. **Карантин.** QC fail → `QUARANTINE` → «вернуть на склад» (→ `RECEIVING`), «вернуть поставщику»
   (→ `RETURN_TO_SUPPLIER`), «списать» (→ `SCRAP`). Последние два выводят товар из физического остатка.
3. **Agnum.** Ежедневный импорт товаров и снимка остатков; физический остаток в MES только после «Paskirstyti»;
   ежедневный экспорт «количество × себестоимость»; продажные цены KN2/KN1 по настройке.
4. **Перемещение.** Ячейка → ячейка одного склада, один шаг через `IN_TRANSIT_{номер}`, обе записи атомарно.
   В `SCRAP` — с утверждением.
5. **Продажа.**
   - Цена из группы клиента или базовой, фиксируется в строке.
   - Pateikti → (утверждение) → Allocate = SOFT-резерв на физических ячейках, «доступно» уменьшается.
   - Release → задания на отбор → отбор: ячейка → `SHIPPING`, резерв на отобранное количество закрывается.
     Частичный отбор оставляет задание на остаток.
   - Упаковка: коробка (HU) со строками содержимого, остаток не двигается.
   - Dispatch: перевозчик и номер вручную; `SHIPPING` → `CUSTOMER`.
   - Отмена до отбора снимает резерв. Отмена после отбора: `SHIPPING` → `RECEIVING`, дальше Putaway.
6. **Волна.** Группа выпущенных заказов; список отбора — их настоящие задания на отбор по порядку ячеек;
   отбор идёт обычным путём заданий.
7. **RMA.** RMA по строкам заказа → приёмка в `QC_HOLD` (товар возвращается в остаток) → осмотр: «на склад»
   (→ `RECEIVING`) или «списать» (→ `SCRAP`). Сумма кредита хранится в RMA, финансового документа нет.
8. **Инвентаризация.** Пересчёт → расхождение → утверждение → остаток меняется на разницу. Ручная корректировка как есть.
9. **Стоимость.** Adjust cost, landed cost, write-down меняют только стоимость.
10. **Производство.** Только выдача в `PRODUCTION`, без изменений.

Не делать: подтверждение приёмки in-transit, партии как ключ и FEFO, документы Agnum, API перевозчиков,
разбиение и слияние HU, выпуск продукции, cross-dock как физический путь, серийные номера в движениях,
несколько физических складов.

## 3. Правила работы

- Один этап = одна ветка `codex/warehouse-complete-<этап>` от свежего `main` = один PR → CI → `gh pr merge --merge --admin
  --delete-branch` → Deploy to Test → проверка «Готово» на test → запись в «Состояние» → сразу следующий этап.
- Каждое исправление остатков — unit-тест, который проверяет запись в Marten или проекцию, а не мок шины.
- Новые тексты UI — ключи в EN и LT `WarehouseResources`.
- Проверка на test: только через обычный UI и API, записи с префиксом `QA-` в примечаниях. Прямой SQL на запись нельзя.
  SELECT для сверки можно.
- Если для проверки нужен временный вход без SSO: только заголовок (без `?qa=`), срок не больше 4 часов, после — удалить,
  как в #315.
- Не трогать: legacy SQL, прод, Sales, Shopfloor, Finance, Portal, MCP, Frontline, `agnum-api-deploy`.
- Факт в коде не совпал с этим файлом: минимальная правка в рамках цели этапа и строка в «Отклонения».
  Если цель недостижима без выхода за файл — остановись и запиши.

**C8b. Применение перестройки регистра стоимости**

Сейчас `ProjectionRebuildService.cs:194-221` меняет таблицу только при совпадении checksum, поэтому исправить неверный
регистр нельзя. Для `OnHandValue` и только для него:
1. При расхождении `/projections` показывает изменения из shadow против рабочей таблицы: добавленные, удалённые,

3. API применения получает оба checksum из показанного сравнения; под advisory lock пересчитывает их; если любой
   изменился — 409 «данные изменились, запустите заново»; иначе swap и запись в существующий журнал аудита
   (пользователь, причина, число строк, оба checksum).
4. Поведение остальных проекций и обычный verify не меняются. Тексты EN и LT.
Тесты PostgreSQL: сравнение верное; применение меняет таблицу; устаревший checksum → 409; не админ → 403.
