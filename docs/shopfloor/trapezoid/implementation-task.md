# Задание разработчику / Codex: расчёт трапециевидных вертикальных жалюзи

## Цель и границы

Добавить в существующую работающую Gamyba отчёт **Vertikalios · Trapecija** с автозаполняемой редактируемой формой, серверным расчётом по `trapnew.xls`, динамической SVG-схемой, сохраняемыми версиями и PDF. Пользователь подтвердил текущие вычисления Excel: сначала обеспечить совместимость, затем отдельно обсуждать изменения правил.

В поставку входят input-поля, а не только renderer. Источник данных — живые заказы, материалы и состав GU. Повторное подключение всей Gamyba, создание нового Reporting-модуля, перенос SQL/VBA в браузер, запись уточнений обратно в Sales, оптимизация раскроя рулона и изменение производственных статусов не входят в задачу.

Прочитать [дизайн](designer-task.md), [разбор формул](excel-analysis.md), `AGENTS.md`, `docs/i18n/README.md`. Использовать текущие границы модулей и существующие права/API. Не коммитить без указания пользователя.

## 3. Автозаполнение с ручным fallback — обязательный контракт

Загружать выбранный продукт по стабильному `productId/barcode`, с контекстом заказа/GU и ревизией. Порядок и происхождение:

| Поле расчёта | Приоритет источников |
|---|---|
| `controlType` | Явный A/B из управления изделия (`Valdymas` или соответствующий текущий контракт) → ручной выбор |
| `slatWidthMm` | Подтверждённая ширина **ламельного материала** 89/127 → согласованный slot 1 изделия/типа как явно обозначенный fallback → ручной выбор |
| `widthMm` | Ширина выбранного изделия (`Plotis`) → ручной ввод |
| `tallHeightMm` | Положительный параметр большой стороны (slot 2) → положительная общая высота изделия (`Aukstis`) → ручной ввод |
| `shortHeightMm` | Положительный параметр малой стороны (slot 3) → ручной ввод |
| `overhangMm` | Явно заполненный slot 4 → для A ручной ввод/явное подтверждение 0; в B расчёт его не использует |
| `highSide` / `viewSide` | Достоверные данные ориентации, если существуют → явный выбор; не выводить из A/B |

Для материала проверить, что речь о ширине ламели 89/127, а не ширине рулона. В текущем исследовании подтверждены slots изделия, **конкретное структурированное поле ширины материала ещё не проверено**. Найти его в текущем material API/SQL и документировать точный mapping. Если нет — расширить read model или показывать fallback; не выдумывать свойство DTO. Разбор текста названия материала может быть подсказкой, но не доказанным значением.

Расхождения материала и slot 1 не скрывать: вернуть оба кандидата, `SourceConflict`, потребовать явного выбора оператора. При несовпадении общей высоты и отдельного параметра большой стороны приоритет у специального параметра; показать исходные данные в деталях. A/B нормализовать `Trim().ToUpperInvariant()` только для известных кодов, не превращать «левое/правое» в A/B.

У каждого поля хранить `{originalValue, suggestedValue, effectiveValue, sourceKind, sourceField, overriddenBy, overriddenAt}`. `null` и 0 различаются: ширина/высоты 0 — отсутствующий/недопустимый размер; выступ 0 — допустимый. Значение `AB` на схеме означает малую высоту, а `controlType=A/B` — механизм, не смешивать имена.

Оператор может изменить любое основное поле. После редактирования оно помечается `Manual`; обновление данных заказа не стирает уточнение. «Вернуть из источника» снимает override для одного поля. При переключении изделия не переносить предыдущие размеры в новый продукт. Черновики привязаны к идентификатору изделия; смена материала заново проверяет ширину ламели и конфликт.

## 4. DTO и чистый вычислитель

Предлагаемая форма, адаптировать имена под текущие Contracts:

```csharp
public sealed record TrapezoidInputs(
    string ControlType, decimal WidthMm, decimal ShortHeightMm,
    decimal TallHeightMm, int SlatWidthMm, decimal OverhangMm);

public sealed record TrapezoidSlat(
    int Number, double FinishedLengthRawMm,
    double CutLengthRawMm, decimal CutLengthDisplayMm,
    double AlongRailMm, double HorizontalMm);
```

Контекст документа отдельно: `GuId?`, `OrderId`, `ProductId`, `Barcode`, `SourceRevision`, `MaterialId`, `Quantity`, `HighSide`, `ViewSide`, `FieldOrigins`, `TechnologyProfileVersion`, `LookupTableVersion`, `AlgorithmVersion`.

Результат: `Status`, `ValidationIssues[]`, геометрия/угол, `RailBlankMm`, `RailCutMm`, `FixedOffsetMm`, `FixedToMechanismMm`, `FreeOffsetMm`, `LookupWidthMm`, `BaseCount`, `ExtraCount`, `SlatCount`, `PitchMm`, `SpacerCutMm`, `ExtenderMm`, `Slats[]`, `CutTotalRawMm`, `FabricUsagePerProductRawM`, `FabricUsageTotalRawM`.

Ввод/контракты могут использовать decimal; тригонометрия в .NET использует double. Результат сверять с Excel в заданном допуске. Округление на выходе явно задаётся, например `MidpointRounding.AwayFromZero` для положительных размерных значений, с тестами половинных случаев. Не использовать default banker rounding без проверки. Не округлять промежуточные величины и длины перед суммированием.

Алгоритм подробно дан в [excel-analysis.md](excel-analysis.md), исполняемая спецификация в [reference-calculator.mjs](reference-calculator.mjs). Перенести формулы в .NET как одну чистую функцию `Calculate(inputs, technologyProfile, lookupTables)`. Не выполнять строки Excel/SQL из шаблона и не держать независимые вычислители на клиенте и сервере. JS в HTML — только проверяемый прототип; production preview и PDF читают один серверный результат.

Профиль `legacy-trapnew-v1`: 5/25/16/15/130, запас рамы 0, +6 к детали шага, -5.5 до механизма, +45 к ламели, +27 к расходу. Версионировать вместе с таблицами. Пользователь подтвердил сохранение +45/+27; уточнение их исторического смысла не блокирует совместимый перенос.

Сохранить особый `LOOKUP` для 89 мм с добавкой в обе колонки. Не заменять его «более логичным» `max(n0,nRequired)` без отдельного согласованного изменения. Сжатие справочников допустимо только при полном совпадении по каждому исходному ключу.

## 5. Валидация и пересчёт

- Проверить A/B, 89/127, все требуемые значения, конечность, `w>0`, `ht>=hs>0`, целое положительное количество комплектов, `o>=0`.
- Не переставлять местами высоты молча. Показать ошибку или явное действие «Поменять высоты местами» с согласованным изменением ориентации.
- `n0<2`, неположительный рабочий пролёт/длина реза, отрицательная длина ткани, нечисловой удлинитель — не готовый расчёт. Ошибка имеет код/поле и локализованный текст.
- Границы таблиц не экстраполировать молча. Значения вне извлечённой области — `OutsideReferenceDomain` с объяснением, что этот режим ещё не проверен. Это ограничение первого релиза, а не заявленный физический предел изделия.
- Для >78 ламелей сначала сверить алгоритм и старый ограниченный SUM, затем добавить полное суммирование/пагинацию как явное расширение. Не выдать первые 78 за полный результат.
- Отсутствующая зеркальность не меняет длины, но не должна давать произвольный монтажный чертёж. До выбора разрешён нейтральный вид «от короткой к длинной» с явной подписью; финальная ориентация документа должна быть определена.
- Debounce ввода, отмена предыдущего запроса или sequence ID. Поздний ответ для предыдущих размеров не может заменить свежий результат. Input invalid/pending → старый результат не доступен для печати как текущий.

## 6. Сохранение и документы

Использовать существующий реестр `gam`. Добавить новый стабильный `reportKey`, независимый от EN/LT подписи. UI получает размер каталога и применимость с сервера; не оставлять hardcoded 13. Существующие отчёты не удалять и их dataset не менять.

Пример границ операций (маршруты согласовать с актуальным API): получить input-кандидаты изделия; рассчитать черновик; сохранить расчёт с expected revision; сформировать документ из сохранённого расчёта; получить конкретный PDF. Не привязываться к выдуманному endpoint из этой спецификации.

Версия расчёта сохраняет effective input, оригинальные значения и provenance, результат всех ламелей, количество/материал, ориентацию, версии алгоритма/таблиц/профиля, автора и время. Документ дополнительно фиксирует template version, locale, snapshot hash и PDF artifact ID. Все данные для повторной печати доступны без повторного чтения изменившегося заказа.

При изменении заказа после расчёта показать различие; автоматически не пересчитывать архив. При формировании по устаревшей source revision вернуть conflict и позволить явно обновить исходные данные либо сохранить обоснованное уточнение в рамках принятых прав. Не затирать ручные значения. Reprint открывает тот же artifact; «Новая версия» создаёт новый immutable snapshot.

Повторный запрос сохранения/PDF должен быть идемпотентным. Права: чтение конкретного GU/заказа, редактирование расчёта, генерация/просмотр архивного документа проверяются сервером. Повторная печать не выдаёт изделие в производство, не меняет готовность и не списывает ткань.

В редакторе шаблона разрешены размещение/подписи/колонки готового dataset и SVG. Нельзя редактировать технологические формулы как текст шаблона. Выбор PDF-движка согласовать с текущим контуром; не навязывать новый движок по старому документу миграции.

## 7. SVG и WebUI

Renderer получает готовые `Slats[]`; значения таблицы, tooltip и SVG берутся из этого массива. `x[i]` использует горизонтальную проекцию шага `pitch*cos(alpha)`, длины на виде сборки — `FinishedLengthRawMm`, на виде раскроя — `CutLengthRawMm`. Монтажный контур по AD/AB/CD рисуется отдельно: нельзя растянуть готовые ламели так, чтобы крайние длины принудительно совпали с введёнными высотами.

Строго один масштаб X/Y, padding под размеры, стабильные номера от короткой к длинной; зеркалирование меняет расположение, не массив длин и не A/B. Габариты фурнитуры и смещения начала координат проверить по реальному изделию перед выпуском сборочного чертежа. Прототип иллюстрирует масштаб ткани, а не подтверждает все монтажные узлы.

SVG текст/цвет/материал экранировать, не принимать произвольный SVG от клиента. На сервере формировать безопасную геометрию либо встраивать доверенный renderer. Не использовать растрированный шаблон трапеции.

Существующие local classes, MudPaper outlined/elevation 0, плотные таблицы и custom chips. Любой новый текст WebUI, ошибка, aria-label и PDF-лейбл — ресурс EN/LT через `IStringLocalizer`; не копировать старый helper `L("EN", "LT")` в новые компоненты. Статический HTML в docs является отдельным дизайн-прототипом.

## 8. План реализации и приёмка

1. Сверка актуальной Gamyba и mapping данных. Read-only загрузка реального изделия: A/B, материал 89/127, ширина, высоты, quantity, source revision. Зафиксировать контракт источника и все fallback.
2. C# calculator + immutable профиль/таблицы. Эталоны из `fixtures.json`, послойные численные проверки и все границы таблиц. Сравнить с используемым производством Excel.
3. Input-форма с происхождением значений, manual override/reset, server preview и защитой от устаревших ответов. Сценарий AD=1970, отсутствующие AB/CD обязателен.
4. SVG + связь с таблицей, раскрой/сборка, зеркало и quantity. Сравнить численные значения с calculator, а не тестировать только наличие элементов.
5. Сохранение/ревизии/PDF/NoData/права/реальный каталог отчётов. Архивная печать после изменения заказа должна воспроизводить исходные значения.

Обязательные тесты: A/B × 89/127; два сохранённых эталона и **каждая** длина; +45/+27 и raw total; выступ 0/10 для A и отсутствие его влияния в B; плоская/почти плоская геометрия; смена материала 89↔127; конфликт material/slot1; general-height fallback; отсутствие данных/0/null; ошибочный A/B; изменение изделия; сохранность manual override; границы 499/500, 610/611, 717/718, 1846/1847, 4079/4080; удлинитель на округлённых 0/1/25/26/50/51/75/76; ветка extra89; quantity>1; 78 и выход за область; stale request/revision; EN/LT; PDF на несколько страниц; отсутствие доступа; отказ render и идемпотентный retry.

Definition of done: оператор выбирает настоящее изделие, получает доступные значения автоматически, заполняет пропуски, меняет размеры, видит пересчитанные ламели, сохраняет конкретную версию и печатает совпадающий документ. Числа сверены с Excel; повторная печать не зависит от текущего заказа. `dotnet build` и релевантные unit/integration/UI проверки проходят; изменения производства/остатков отсутствуют.
