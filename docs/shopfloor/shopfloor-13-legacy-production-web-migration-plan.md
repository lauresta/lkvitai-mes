# Перенос всего контура Gamyba из Access в web

Статус: этап 1 реализован в Razor на fixtures и развёрнут на test; UX-проверка продолжается. На этапе 2 подключены защищённая очередь G02, просмотр GU/состава G04 и первичный поиск изделия/документов G11 под legacy SQL identity; на test страница Gamyba показывает их только для чтения. Остальные экраны и производственные команды ещё не подключены к базе. Неизвестные контракты закрываются на этапе 0, а не угадываются при написании команд.

Дата / review: 2026-11-02.

Основной модуль: **Shopfloor**. Повторно используем Sales, Scanning и Warehouse в пределах уже существующих возможностей; запуск новых Quality, Delivery и Reporting не входит в эту работу.

## 1. Результат и границы

Оператор и руководитель производства должны выполнять в web все действующие операции старого производственного контура: от подтверждения и выдачи изделий в цех до регистрации готовности, ремонтов, складских операций, печати и передачи готовой продукции. После проверки каждого сценария Access перестаёт быть необходимым для этого сценария.

Это план всего контура, а не только PDF или редактора отчётов. Полнота определяется реестром Access → web и проверкой сценариев, а не количеством новых экранов.

Первый выпуск сохраняет общую legacy SQL-базу, существующие штрихкоды, идентификаторы, статусы, процедуры и аудит. Шаблоны, печатные задания и служебные состояния Cikada могут храниться в PostgreSQL. Дублирующий источник истины для производственных статусов и остатков не создаём.

Существующие Shopfloor Production Families / Workflows / Work Centers / Work Stations сохраняем. Их наличие не означает, что очередь оператора уже реализована: текущая Operator Queue — iframe-прототип. Полноценный новый движок маршрутов, автоматическое планирование загрузки и digital twin — отдельное развитие после переноса действующих Access-сценариев, а не обязательная предпосылка этого переноса.

### Фиксация scope

- **Переносим:** действующие операции Gamyba / Produkcija и вызываемые ими формы, контекстные действия, проверки, отчёты и этикетки. Производственные ремонты, технологические настройки и складские/отгрузочные действия входят только в объёме конкретных подтверждённых legacy-сценариев G01–G15.
- **Повторно используем:** готовые ввод/подтверждение Sales, Cikada identity mapping и существующие публичные контракты модулей. Их регрессионная проверка обязательна; повторная реализация не нужна.
- **Не строим в рамках переноса:** новый MES routing engine, планировщик мощностей, StockLedger/систему резервирования, универсальный BI/reporting-конструктор, редактор EPL-этикеток, систему согласования технологических изменений, бухгалтерию/зарплату/логистику или новые модули целиком. Бесплатный редактор ограничен перечисленными печатными формами и их разрешёнными полями.
- Обнаруженный действующий производственный сценарий добавляется как дочерняя строка Gxx и покрывается переносом. Архивная форма, пожелание новой функции или исправление старого бизнес-правила — отдельный issue и решение владельца; не повод автоматически расширять работу. Исключение действующего сценария также требует явного решения, а не отметки «потом».
- Экраны ремонтов, передачи готовой продукции и производственных отчётов размещаем в Shopfloor. Planned-модули Quality / Delivery / Reporting не становятся зависимостью завершения; ссылки в них возможны позже, без второго владельца операции.

Изменение бухгалтерии, расчёт зарплат с нуля, оптимизация SQL, новый Sales UI и исправление общей ошибки аннулирования заказов не включаются автоматически. Связанные действующие производственные вызовы и их последствия должны быть обследованы и покрыты сверкой; отдельные изменения — в issues.

## 4. Критические правила совместимости

1. Состояния и разрешённые переходы брать из legacy, включая `fn_CheckStateChange` и SQL-источник разрешённых операций. Не задавать универсальную линейную цепочку поверх старой системы.
2. Подтверждение Sales, выдача GU, сканирование готовности, остановка производства и отмена заказа — разные команды.
3. Атомарность — на одну бизнес-команду: создание GU с первой выбранной порцией (если это один пользовательский шаг) либо добавление следующей порции в текущее GU. Access создаёт пустой GU через `NewTask` и допускает несколько `Gaminti` в нём; этот сценарий не терять и не подменять несуществующим lifecycle «закрыт/опубликован». Границы допустимого дополнения/пустого документа зафиксировать в coverage. Каждую порцию вставлять одной SQL-транзакцией, по одной строке на statement: триггеры используют скалярные значения. Отказ откатывает только текущую команду целиком, не ранее выданные порции.
4. Повторный запрос после тайм-аута должен возвращать результат исходной команды. Нужен сохраняемый command receipt в одной транзакции с legacy-записью; отдельно хранимый PostgreSQL-флаг не обеспечивает атомарность с SQL Server.
5. До write-этапа проверить возможность безопасного использования существующего receipt-контракта либо подготовить изолированное расширение для Shopfloor. Sales receipt/revision привязаны к одному заказу: нельзя механически применить их к GU из нескольких заказов/серий. Receipt сохраняет scope всей команды, hash неизменного запроса, результаты и идентичность; повтор с другим payload — конфликт, timeout — проверка результата исходной команды, не новый command ID. Любое DDL общей production-базы — отдельный проверяемый скрипт и согласование, не скрытая миграция.
6. Номер GU назначать с защитой от конкурентного `COUNT+1`, включая одновременно работающий Access. Web-only lock / `sp_getapplock` не защищает от клиента, который его не использует. Подтвердить стратегию на фактической схеме и конкурентном тесте Access+web; без неё write-ветка не готова. Не рассчитывать на `@@IDENTITY`; получать ID с учётом триггеров. GT, ручные номера, смену суток/года и используемые prefix-фильтры проверить отдельно, без самовольного изменения формата.
7. Перед записью повторно проверять права, состояние, доступность и версию выбранных изделий: Access может изменить их после загрузки списка. Два оператора не должны выдать одно изделие дважды по устаревшему экрану.
8. Во все legacy-операции передавать доверенную Cikada-идентичность через mapping / `EXECUTE AS LOGIN`, с гарантированным REVERT. Дополнительно ограничивать выборки и прямые URL: очередь/отчёты не везде сами вызывают `Loc_leidimas`.
9. Перенести в Shopfloor проверенный native/SSO mapping-контракт; существующий общий authenticated/structured-bearer policy не считать достаточным для новых производственных записей. Неподписанные роли/логины от клиента не принимать.
10. Каждый штрихкод обрабатывать как строку; сохранить существующую длину, формат, привязку и единицы. Повторный скан должен давать понятный результат, а не дублировать операцию.
11. Не копировать глобальный `VARS.FlagYesNo` как web-блокировку. Выяснить его действующие зависимости; использовать блокировки конкретной операции/партии без остановки других пользователей Access.
12. Списания и печать не связывать неявно. Повторная печать не меняет статус и не создаёт складские движения.
13. Обнаруженные противоречия старых правил фиксировать, а не исправлять без решения владельца: в частности, очереди по-разному используют дату заказа/изделия и особую заметку об отмене по просьбе клиента.
14. Исправление ошибочного скана — отдельная команда с receipt и проверкой актуального состояния: штатный `DELETE` одной допустимой строки `TAB_ProductionOutputDocumentDetails` вызывает восстановление предыдущего статуса триггером. Позднейшая операция запрещает такое исправление. Не обходить триггер прямым UPDATE статуса; запретить произвольное удаление истории. В проверенном триггере audit-вызовы закомментированы: не обещать существующий delete audit. Receipt команды должен сохранить actor, документ/код, прежнее и результирующее состояния без изменения общего legacy-триггера.
15. GU может содержать изделия нескольких заказов/филиалов. Проверять весь состав до выдачи, чтения полного документа, рендера и печати; не выдавать чужие строки или агрегаты через ID задания. Зафиксировать legacy-политику смешанных документов; до её подтверждения полный документ с недоступными строками не выдавать. Пустой документ проверять по владельцу/разрешённой операции: отсутствие строк не делает его общедоступным. Кэш, receipts, jobs и архивы не должны обходить текущие права; отсутствие mapping не даёт fallback на `sa`.
16. Групповая выдача — атомарная порция; сканирование и импорт — последовательность отдельных результатов по кодам, как в Access. Ошибка одного кода не откатывает ранее принятые сканы и не приводит к повтору уже принятых при возобновлении. Размер партии, ведущие нули/пробелы, формат 12-символьных кодов и частичный результат проверить на эталонах; не выполнять молчаливую опасную нормализацию.

### Различие с будущей архитектурой Shopfloor

`shopfloor-00-architecture.md` описывает целевой процесс «резерв при release, фактическое потребление при completion». Действующая `SP_WriteOffBlindComponentsNew` создаёт legacy-движение и выставляет ему `bConfirmed=-1` уже внутри процедуры. Это разные бизнес-процессы.

На этапе совместимости сохраняем подтверждённое поведение Access за явной командой списания. На этапе 0 установить её фактическое место вызова, проверки и возможность повторения/отката; уже подтверждённое движение не проводить ещё раз по устаревшему тексту сообщения Access. ### Выбор движка: обязательная проверка до массового переноса

Первый кандидат — pdfme (MIT, встраиваемый web designer). Не фиксировать его как окончательный до пилота:

- Снять из Access эталоны Roletai и более сложного отчёта с группировками/переносами/подотчётами.
- Проверить редактирование полей и колонок, динамические таблицы на несколько страниц, повторные заголовки, итоги, длинные примечания, шрифты LT, штрихкоды и размер бумаги.
- Проверить ограничения designer: `staticSchema` для колонтитулов сейчас не редактируется визуально. Любые необходимые дополнения к редактору оценить явно.
- Пользователь с правом редактирования шаблона должен добавить поле из набора данных, изменить расположение/ширину/подпись, сохранить, открыть заново и получить одинаковый результат preview/render.
- Добавление отсутствующего поля/формулы в SQL/API остаётся задачей расширения dataset, а не произвольным доступом конструктора к SQL.
- Шаблоны с динамическими переносами создавать на размерном blank basePdf; импорт готового PDF не считать автоматическим переносом Access layout.
- Если критическая форма не воспроизводится либо web-редактор требует несоразмерной доработки — представить результат владельцу и выбрать альтернативу. FastReport Open Source + бесплатный Windows Community Designer — возможный .NET-вариант, но это не бесплатный встроенный web-редактор. Платные лицензии без решения не покупать.

### Контракт после выбора движка

`.NET API → авторизованный legacy dataset → renderer → PDF + сохранённая версия`.

Шаблон имеет стабильный код, engine/version, dataset version, Draft/Published, автора/время и неизменяемые опубликованные версии. Редактор получает только разрешённый dataset и тестовые значения; SQL credentials и произвольные подключения в браузер не передаются.

Архив хранит использованный dataset с моментом его получения, состав/ревизию документа, версии шаблона/renderer, готовый PDF и контрольную сумму. Снимок для печати не объявлять снимком на момент GU commit, если он прочитан позже. Повторная печать открывает исходный документ; актуальная регенерация оформляется отдельно. Дополнение GU или исправление скана не переписывает ранее выпущенный PDF: UI показывает, что состав изменился, и предлагает новую версию. Сбой до фиксации снимка допускает только явную генерацию из актуальных данных, без обещания точного восстановления прежнего документа.

На этапе 0 проверить использование/доступность старых архивов `\\bazesvr2\Documents\GAMYBA\ZALIUZES\Isduota_gamybai` и `\\baze\Isdavimai`. Если исходный PDF существует, предоставлять его через авторизованный серверный доступ по документу; не заменять молча регенерацией. При отсутствии — явная пометка «создано из текущих данных». Массовый импорт файлов, перестройка SMB и универсальный архив документов вне scope; невозможность доступа фиксируется как ограничение конкретного сценария.

Обычная бумажная печать первой версии: PDF preview → штатный диалог печати браузера. Приёмка включает реальный принтер, размер/ориентацию/поля, масштаб 100% и многостраничный документ. Автоматическая печать без диалога/на заданный принтер не включается предположением; если это необходимая часть действующего рабочего процесса, фиксируем её на этапе 0 и отдельно определяем минимальный способ реализации.

Публикация включает проверку на реальном коротком/длинном задании и возможность вернуться к предыдущей опубликованной версии. На первом этапе UI конструктора EN/LT можно ограничить доступными переводами движка, но собственные действия/ошибки/права Cikada обязаны быть EN/LT; остаток локализации конструктора фиксируется явно.

## 7. Этикетки и COM-агент

Сохраняем EPL и существующие штрихкоды. Данные брать из проверенного контракта `SP_GamHorizontaliosLabelsByTask` / `sp_BlindDescriptionByBarCode` с дополнительным серверным контролем доступа.

Поддержать:

- печать задания, одного изделия и разрешённый ручной режим;
- флаг `bPrintLabels`, исключения ремонтов, `sLabelTypeName`, группы этикеток;
- разделители по группе, дополнительную этикетку без barcode, специальный текст `JUOSTOS` / PPP10;
- количество экземпляров по реальной legacy-логике: VBA отправляет `P1` на строку, количество изделия печатает как текст; не умножать наклейки автоматически без проверки;
- сортировку и последовательность; типографику/кодировку, литовские буквы и лимиты полей; безопасное экранирование EPL;
- возможность повторить выбранные этикетки, а не всю пачку;
- паузу между отправками, продолжение и отмену оставшейся части с сохранением позиции; уже отправленные байты/этикетки отменёнными не считать.

Архитектура: web → сохраняемое печатное задание → локальный Windows service/agent → COM → Zebra. Агент получает задания исходящим HTTPS-запросом, не требует публичного COM-прокси. Привязка к зарегистрированному рабочему месту/принтеру, аутентификация и отзыв доступа; без legacy SQL-пароля в агенте.

Одна очередь на физический принтер, блокировка COM, настраиваемая скорость подачи, тайм-ауты, restart и журнал попыток. Access также открывает этот COM: для каждого рабочего места зафиксировать переключение владельца «Access / web-agent». Занятый порт — ожидание/ошибка без отправки; два источника не перемешивают пачки. Автоматическое определение offline/бумаги допустимо только при подтверждённом ответе данной модели; иначе статус сообщает оператор, а не выдумывает агент.

Печатное задание фиксирует последовательность **физических этикеток**, включая разделители и дополнительные, исходные EPL-байты, версию формата, профиль принтера и исход каждой попытки. Строка изделия, количество изделий и число этикеток — разные счётчики. Повтор диапазона использует сохранённые байты; новый запрос к SQL означает новую генерацию. Lease/fencing и локальный журнал агента должны исключать повторную отправку после потери ответа/перезапуска; при неизвестном исходе — `Uncertain`, не автоматическое воспроизведение пачки другим worker.

Различать Pending / Claimed / Sending / Paused / Sent / Failed / Uncertain / Cancelled, с отдельным исходом каждой этикетки. Доставка байтов в COM не доказывает, что этикетка физически вышла. При обрыве после отправки не делать слепой автоматический reprint: показать неопределённый результат и дать оператору повторить конкретный диапазон. Не обещать физическую exactly-once печать без подтверждения оборудования.

## 8. Технические границы

- Shopfloor.Contracts — DTO и стабильные коды ошибок; Application — сценарии и порты; Infrastructure — SQL/EF/render/print adapters; API — политика/HTTP; WebUI — только Contracts и building blocks.
- Не ссылаться на Sales/Warehouse Infrastructure из Shopfloor. Общий безопасный механизм identity/SQL context выделять только при необходимости; взаимодействие модулей — через публичные контракты/API.
- G14 test-before-save: текущий Sales preview загружает уже сохранённые формулы, поэтому не считать его готовым API проверки новой формулы. Переиспользовать существующий чистый calculator через минимальный общий компонент либо узкий авторизованный контракт с теми же ограничениями функций/входов. Не писать формулу временно в production для проверки, не вводить произвольное выполнение VBA/SQL и не дублировать parser.
- `Production Family` / workflow template и `Report Template` — разные сущности с разными жизненными циклами.
- PostgreSQL: версии шаблонов, артефакты/метаданные, очереди/попытки печати, настройки принтеров и служебная история; бизнес-статус изделия читается из legacy.
- PDF/снимки/EPL — постоянный защищённый volume + метаданные в существующем Shopfloor PostgreSQL; достаточно текущей инфраструктуры, отдельная платформа object storage не требуется. Не `/tmp` и не память процесса. Retention и доступ должны учитывать персональные данные и существующую privacy-логику Sales; сохранённый артефакт не должен возвращать сведения, скрытые последующей privacy-операцией.
- Долгие PDF/печать — фоновые задания. Страница показывает progress/result и не блокирует оператора ожиданием COM или рендера.
- Взаимодействие SQL и PostgreSQL не объявлять одной транзакцией. После legacy commit создание артефактов должно быть восстанавливаемым по существующему документу; сбой PDF не откатывает уже реально выданную партию.
- Фоновые jobs сохраняют доверенного инициатора и scope; повторно проверяют применимые права перед чтением/рендером/отправкой. Worker не использует полномочия `sa` вместо пользователя. Receipt исходной бизнес-команды и текущий статус печати различать; ошибка печати не означает отказ выдачи GU.
- Приёмка миграций, persistent volumes, ключей аутентификации, users и feature flags обязательна; очередной deploy не должен возвращать прототип или терять очередь.

## 10. Тестирование и release

- Unit/contract: eligibility, переходы/права на строки/действия/поля, dataset/schema, номера/receipts, шаблоны, EPL и COM-протокол. Один command ID с другим payload, потеря ответа после commit, изменённый состав GU, полночь/смена года и отзыв прав должны иметь определённый исход.

Не считать rollback на production безопасной песочницей для внешних side effects. До пробы проверить связанные складские/финансовые изменения и уведомления.
- UI: реальный browser на удалённом test; EN/LT, Tab/select-all, scan + Enter, видимые ошибки, несколько вкладок, истёкшая сессия, SSO/native login, восстановление после deploy.
- Печать: текст/значения/группы/итоги/NoData + визуальная сверка PDF; реальная бумага и COM-этикетки; reader находит то же изделие в Access. Отдельно pause/resume/cancel remaining, занятой Access порт, недоступный агент, потеря ack, lease/restart и сохранённый EPL после изменения изделия. Ошибка renderer/агента не повторяет выдачу GU.
- Нагрузка: измерить время загрузки очереди, выдачи партии согласованного рабочего размера, результата скана и фоновую скорость печати; после baseline зафиксировать численные цели. Диагностику старой SQL-задержки S2-012 не маскировать UI-тайм-аутами.
- Production SQL общая. Автотесты — изолированная среда. Разрешённые business-записи — Testavimas; это не автоматическое разрешение на реальные списания, изменение глобальных справочников, отгрузку или печать целой пачки.
- Отдельные feature flags для task release, scan mutations, stops/repairs, stock operations, dispatch, template publish и physical printing. По умолчанию выключены до готовности соответствующей ветки.
- На test ограничивать запись по **каждому** изделию/заказу состава и реальной серии Testavimas, а не названию салона, номеру GU или правам admin. Повторно проверять scope при дополнении GU, импорте, исправлении и создании связанных документов. Смешанная недопустимая порция не должна частично пройти.
- Каждый согласованный выпуск merge в main, обычный CI/deploy, проверка точного SHA образов, здоровья модулей, миграций и сохранности очередей/ключей. Не оставлять рабочую версию только в ручном образе или неслитом PR.
- Откат UI/feature flags не откатывает уже совершённые legacy-операции. Восстановление — через разрешённые нативные команды/переходы и audit, включая проверенное исправление последнего скана, без массового удаления истории. Перед пилотом проверить возврат рабочего места на Access и освобождение COM, сохранность созданных GU/GT, архивов и исходов печати.
